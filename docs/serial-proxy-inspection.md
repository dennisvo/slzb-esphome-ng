## 1. Executive summary

Two clean findings, one good and one that reshapes Phase 1.

### ✓ `serial_proxy` exists, is first-class in mainline ESPHome, and fits our design almost verbatim

- Lives at `esphome/components/serial_proxy/` in mainline (no external component needed).
- Marked **experimental** by upstream — API may change without notice.
- Deep API integration: dedicated proto messages, `USE_SERIAL_PROXY` compile define, `SerialProxyDataReceived` frames flow over the already-encrypted Native API connection.
- `MULTI_CONF = True` — multiple instances are officially supported (perfect for MR4U's 2 radios, ULTIMA's 3).
- Subscribe/unsubscribe model with port-claiming (`port_claimed_by_other_`) — one API client can hold a port at a time. Prevents split-brain access.
- Includes optional modem-control pins (`rts_pin`, `dtr_pin`) for line-state signalling (see §5).

### ✗ ESPHome's `uart:` component does **not** support CTS/RTS HW flow control at all

- No `cts_pin`, no `rts_pin` in the `uart:` config schema (searched `esphome/components/uart/__init__.py` — only `flow_control_pin` singular exists, which is the RS485 half-duplex direction pin, unrelated to CTS/RTS).
- No calls to ESP-IDF's `uart_set_hw_flow_ctrl()` anywhere in the ESPHome tree.
- The `flow_control` parameter in the `SerialProxyConfigureRequest` proto message exists (a client can request it), but the current implementation explicitly rejects it: `"Hardware flow control requested but is not yet supported"` → returns `SERIAL_PROXY_RESULT_NOT_SUPPORTED`.

This **retracts** the assumption in `hardware-map.md` §6 and `design.md` Phase 1 step 6 that "we just add `cts_pin`/`rts_pin` to the UART bus package YAML." That YAML surface doesn't exist. **Phase 1's flow-control step needs to be replanned.** See §7.

## 2. `serial_proxy` YAML surface (from `esphome/components/serial_proxy/__init__.py`)

```yaml
serial_proxy:
  - id: <auto-generated or explicit>
    name: <string, required>          # human-readable port name (surfaced in API)
    port_type: TTL | RS232 | RS485    # required
    uart_id: <existing uart bus id>   # from uart.UART_DEVICE_SCHEMA
    rts_pin: <optional GPIO pin>      # modem RTS output, driven via SetModemPins RPC
    dtr_pin: <optional GPIO pin>      # modem DTR output, driven via SetModemPins RPC
```

Notes:
- `port_type` — TTL vs RS232 vs RS485 is signalling only (informational for the client); the actual electrical layer is the underlying UART bus.
- `rts_pin` / `dtr_pin` are **NOT** for HW flow control. They're generic GPIO outputs the API client can toggle via `SerialProxySetModemPinsRequest`. Useful for e.g. driving a "reset" or "bootloader-enter" line indirectly, but not for automatic CTS/RTS backpressure. (Our existing reset/flash GPIO switches remain the right mechanism for that — see hardware-map §4/§5.)
- `MULTI_CONF = True` — declare as many `serial_proxy:` list items as radios.
- `DEPENDENCIES = ["api", "uart"]` — cannot exist without an `api:` block. Perfect fit for our design.
- Codeowner: `@kbx81`.

## 3. Runtime behavior (from `serial_proxy.h` and `.cpp`)

### Loop-level UART reading

```cpp
// serial_proxy.h
inline constexpr size_t SERIAL_PROXY_MAX_READ_SIZE = 256;
```

Per instance, per ESPHome loop iteration, `serial_proxy` reads **up to 256 bytes** from the UART FIFO and forwards them as a single `SerialProxyDataReceived` API message. Uses a **stack** buffer (not heap-allocated per read).

This resolves design doc §21.2 ("Whether the 256-byte-per-loop forwarding sustains EFR32 burst patterns without loss"): confirmed as the actual value in current ESPHome. Whether it *sustains* burst patterns is an empirical question for Phase 3/5.

### Setup priority

```cpp
float get_setup_priority() const override { return setup_priority::AFTER_CONNECTION; }
```

`serial_proxy` sets up after the API/network is ready, avoiding a race where UART data is generated before the API pipe exists.

### Port claiming

```cpp
bool port_claimed_by_other_(api::APIConnection *api_connection) const;
```

Only one API client can hold a `serial_proxy` instance at a time. If a second client tries to configure it, it gets `SERIAL_PROXY_RESULT_PORT_IN_USE`. Explicit unsubscribe is needed (or connection drop) before another client can take over. Prevents ZHA and OTBR from stomping each other if pointed at the same port by mistake.

### Configure RPC

```
SerialProxyConfigureRequest fields:
  instance    uint32   which serial_proxy in the list
  baudrate    uint32   new baud
  flow_control bool    (currently rejected — see §1)
  parity      enum     NONE / EVEN / ODD
  stop_bits   uint32   1 or 2
  data_size   uint32   5..8
```

The API client (ZHA / OTBR) can reconfigure UART parameters at runtime. Explicit no-op detection: if new params match current, skips the `load_settings()` call to avoid line-state glitches (a re-apply on some USB-CDC bridges triggers boot-loader entry).

### Write RPC

`SerialProxyWriteRequest`: raw bytes from client → ESP UART TX. No framing, no protocol handling — this is a true byte pipe.

## 4. API integration deep dive

Enums exposed by ESPHome and mirrored in the API .proto:

| Enum | Values | Where declared |
|---|---|---|
| `SerialProxyPortType` | TTL, RS232, RS485 | `api_pb2.h`, `serial_proxy/__init__.py` |
| `SerialProxyRequestType` | CONFIGURE, SUBSCRIBE, UNSUBSCRIBE, SET_MODEM_PINS, GET_MODEM_PINS, FLUSH | `api_pb2.h` |
| `SerialProxyResult` (C++) / `SerialProxyStatus` (proto) | OK, ASSUMED_SUCCESS, PORT_IN_USE, INVALID_ARGUMENT, ERROR, TIMEOUT, NOT_SUPPORTED | `serial_proxy.h`, `api_pb2.h` |
| `SerialProxyLineStateFlag` | RTS (bit 0), DTR (bit 1) | `serial_proxy.h` |

Compile-time gate: `USE_SERIAL_PROXY` is defined only when at least one `serial_proxy:` block appears in the YAML. `SERIAL_PROXY_COUNT` is set to the final instance count at codegen time (needed for API dispatcher arrays).

Message types used on the wire:
- `SerialProxyConfigureRequest` (msg type 138) — client → device, configure UART params
- `SerialProxyWriteRequest` — client → device, TX bytes
- `SerialProxySetModemPinsRequest` — client → device, drive RTS/DTR outputs
- `SerialProxyGetModemPinsRequest` — client → device, read current pin states
- `SerialProxyDataReceived` — device → client, RX bytes from UART
- `SerialProxyInfo` — device → client, per-instance metadata (name, port_type, configured_line_states)

## 5. Modem pins vs UART flow-control pins — do not confuse

Two completely different features, both involving GPIO:

| Feature | Location | Purpose |
|---|---|---|
| `serial_proxy.rts_pin` / `dtr_pin` | Optional in `serial_proxy:` YAML | Generic GPIOs the API client toggles via `SetModemPins` RPC. For legacy modem control (dial-up era) or for repurposing as "reset / bootloader enter" outputs. **Not automatic**. |
| `uart:` CTS/RTS | ~~In `uart:` YAML~~ | **Does not exist.** Automatic hardware flow-control backpressure at driver level. What we actually want for Zigbee/Thread reliability. |

Our design doc §6 (hardware-map) previously conflated these. The `rts_pin` / `dtr_pin` in serial_proxy will not give us the backpressure behavior we want; they will only give us API-driven GPIO toggling.

## 6. Fitness for our design

Mapping `serial_proxy` capabilities onto design doc requirements:

| Requirement (from design doc) | serial_proxy support | Notes |
|---|:---:|---|
| Encrypted transport (no plaintext UART on LAN) | ✓ | Runs over Noise-encrypted Native API — no separate port. |
| Multiple instances (CC26 + EFR32) | ✓ | `MULTI_CONF = True`, tested pattern. |
| Subscribe/unsubscribe from HA-side transport | ✓ | Full protocol support. |
| Reconnect-safe (§21.6) | Partial | Port-claim releases on disconnect; needs empirical verification of state after reconnect race. |
| Radio flashing through the same pipe (§21.7) | Partial | Configure RPC supports runtime baud changes (including down-shift for bootloader speeds). Whether bootloader-mode flashing survives Noise encryption end-to-end needs testing. |
| Radio reset / boot pin control | Via GPIO switches, unchanged | The `serial_proxy.rts_pin` / `dtr_pin` are the *wrong* mechanism for controlling CC26 / EFR32 reset. Our existing `uart1_rst` / `uart1_flash` switches remain the right approach. |
| HW flow control | ✗ blocked | See §7. |

## 7. Flow-control gap — options and recommendation

### The gap

- ESPHome's `uart:` component has no `cts_pin` / `rts_pin` YAML keys.
- No code path in ESPHome ever calls ESP-IDF's `uart_set_hw_flow_ctrl(port, UART_HW_FLOWCTRL_CTS_RTS)`.
- The `serial_proxy` API's `flow_control` bool is accepted at the wire protocol but rejected at runtime with `NOT_SUPPORTED`.

Meanwhile the vendor firmware SLZB-OS (confirmed by web-UI screenshot in `hardware-map.md` §5.3) *does* enable HW flow control on both radios by default. So there's a real-world capability gap between what our secure fork can deliver at Phase 1 vs. what the stock vendor firmware delivers today.

### Options

**A) Upstream ESPHome PR to add `cts_pin` / `rts_pin` to the `uart:` schema and driver.**
- Cleanest, aligns with design doc §22 ("prefer upstream contributions").
- Blocks Phase 1 on external review timelines.
- Reasonable size: add YAML validation + config keys + a small block in `uart_component_esp_idf.cpp` calling `uart_set_hw_flow_ctrl()`, plus optional pin-conflict validation.
- Risk: might get pushback (why isn't this in the existing `flow_control_pin`? — because that's RS485 direction, semantic collision needs a naming discussion).

**B) External component in our fork that extends UART with flow-control support.**
- Fast, unblocks Phase 1 in days rather than weeks.
- Adds fork-local C++ code — first violation of the "no external components" cleanup goal.
- Awkward interaction with upstream `uart:` component (would need to inherit + override, or wrap).

**C) Runtime lambda in Phase 1 firmware that calls ESP-IDF directly at boot.**
- Even faster than (B): a single `lambda:` block in the `esphome:` YAML that calls `uart_set_hw_flow_ctrl(UART_NUM_1, UART_HW_FLOWCTRL_CTS_RTS, 122)` (with the right FIFO threshold constant).
- Requires the ESPHome UART to *not* reconfigure the port later (which it doesn't after setup, unless explicit `set_baud_rate` calls happen — which the runtime baud selector *does*, on every user change). Any reconfig call may reset the flow-control state → race hazard.
- Fragile but instructive as a probe: proves the hardware works before committing to (A) or (B).

**D) Skip flow control in Phase 1 entirely; add later if reliability testing demands it.**
- Matches Phase 6's original "diagnose reliability if problems appear" framing.
- Accepts that our fork's runtime reliability envelope is *slightly narrower* than SLZB-OS's — likely irrelevant at 115 200 baud with light Zigbee traffic, potentially relevant at 460 800 baud for Thread bursts.
- Cheapest by far.

### Recommendation

**(A) as the long-term direction, (D) as the Phase 1 default.** Concretely:

1. **Phase 1**: skip flow control. Ship secure firmware without it. Document the gap explicitly in the fork's README.
2. **Parallel workstream (any time after Phase 1)**: open an upstream ESPHome PR adding `cts_pin`/`rts_pin` support to the `uart:` component on ESP-IDF. Target: land before Phase 3/5 testing so we can validate reliability *with* flow control.
3. **Phase 6** (reliability diagnosis, if problems appear): if the upstream PR hasn't landed by then and we're seeing dropped bytes, evaluate (B) or (C) as short-term unblockers.

This walks back the earlier Phase 1 amendment ("enable HW flow control by default") that was written before we knew ESPHome's `uart:` component doesn't expose the config surface. The reasoning is still sound — flow control is desirable — but the implementation path is now longer than "2 lines of YAML."

## 8. Implications for the design doc

Findings to reflect into `docs/design.md` on the next batched revision:

| Finding | Affects design doc section | Nature of change |
|---|---|---|
| `serial_proxy` exists in mainline, marked experimental | §22 mentions "`serial_proxy` is experimental" — confirmed | No change |
| `serial_proxy` `MULTI_CONF = True` | §8 firmware structure | Confirms multi-instance is officially supported |
| `serial_proxy` reads 256 B/loop stack buffer | §21.2 key unknown | Downgrade to "confirmed at 256 B; behavior under EFR32 bursts still needs empirical validation" |
| `serial_proxy` uses subscribe/unsubscribe with port-claiming | §21.6 key unknown (reconnect behavior) | Confirms mechanism exists; empirical race behavior still unknown |
| `serial_proxy.rts_pin`/`dtr_pin` are for API-driven modem control, NOT for CTS/RTS flow control | §11 / hardware-map §6 | Add clarification; do not conflate |
| ESPHome `uart:` has no CTS/RTS support | Phase 1 step 6, hardware-map §6, §21.3 | Rewrite Phase 1 flow-control step per §7 above; update §21.3 further |
| `serial_proxy` API supports runtime baud reconfigure | §7 native API encryption, Phase 7 (radio maintenance) | May obsolete the current runtime `select` baud selector — HA-side clients can drive it directly. Design decision needed. |

## 9. What Phase 0.2 did NOT inspect

- ESPHome API server-side Noise handshake code path — assumed correct (aioesphomeapi tests would catch breakage).
- Concrete performance of `serial_proxy` under load — that's Phase 3 / 5.
- Whether existing HA integrations already use `serial_proxy` (ZHA / OTBR) — that's Phase 0.3.
- Whether HA's `serialx` transport speaks the `serial_proxy` wire protocol — critical, that's Phase 0.3.

Phase 0.3 (Home Assistant `serialx` inspection) becomes the highest-priority next step, because without `serialx` speaking `serial_proxy` end-to-end, the whole "no host-side software" premise of the design collapses.
